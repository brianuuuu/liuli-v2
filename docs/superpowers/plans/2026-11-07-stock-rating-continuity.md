# 标的评分报告连续性执行文档

> 版本：1.0.50｜日期：2026-11-07｜状态：已审核、待实施
> 基线：云端技能导出提交 `a6169f9f`；用户已批准先提交方案，再实施。

## 1. 目标与范围

1. 在云端现有 11 步流程中补齐固定比较、变动说明、历史验证和后续事项，保留数据校验、同业比较及至少三条本次反证检查。
2. 只扩展评分表三个字段和连续性三类内容，分数、等级、核心逻辑及主要风险继续使用原字段。
3. 本期不做评分方法改版、公式硬校验、贡献分解、历史回填或跨报告内容去重。
4. 领域规则归属 `stock_analysis`，`knowledge_base` 负责解析调度，`basic/report_library` 保存原文，长期架构遵循[系统规格](../../liuli_system_spec.md)。

## 2. 数据契约

### 2.1 存储

| 新字段 | 类型与默认值 | 用途 |
|---|---|---|
| `report_id` | `INTEGER NULL` | 关联真实来源报告，并识别同报告重复导入 |
| `previous_snapshot_id` | `INTEGER NULL` | 固定本次分数比较对象 |
| `continuity_json` | `TEXT NULL` | 保存变动原因、历史验证和后续事项 |

1. 为 `report_id` 增加唯一索引 `uq_stock_score_snapshot_report_id`，允许多条空来源历史记录，不增加日期唯一约束。
2. 两个 ID 使用逻辑关联，不设级联删除，不复制旧分数、分差、原判断全文或完整研究上下文。
3. 来源 ID 由服务端从真实回流记录取得，修订须另存报告并追加快照，不覆盖已保存快照。
4. 三列及索引已获批准，增量迁移后既有记录保持 `NULL`。

### 2.2 报告输出

在 profile 现有 JSON 顶层追加 `previous_snapshot_id` 和 `continuity`，现有评分及其他研究字段保持原位置。

| 连续性数组 | 条目字段 | 数量与含义 |
|---|---|---|
| `change_reasons` | `field / type / reason / evidence` | 发生变化的字段及原因，无变化可为空 |
| `previous_checks` | `snapshot_id / check_id / result / reason / evidence` | 回应全部需验证旧事项，无旧事项可为空 |
| `next_checks` | `id / condition` | 首次建立结构化跟踪时为 1–3 条，后续为 0–3 条新增或实质修订事项 |

1. 三个数组必须存在，接口返回解析后的 `continuity`，数据库仅保存 `continuity_json`。
2. `field` 支持六维分、`investment_level`、`core_logic`、`primary_risk`，总分独立纠错或方法变化时才使用 `total_score`。
3. `type` 为 `new_evidence / judgment_revision / data_correction / method_change / risk_adjustment`，总分原因仅允许纠错或方法变化。
4. `result` 为 `supported / weakened / invalidated / pending / insufficient_evidence`，分别表示支持、削弱、证伪、待验证、证据不足。
5. 原事项身份为 `(snapshot_id, check_id)`，本次 `next_checks.id` 及 `previous_checks` 的引用组合不得重复。
6. `condition` 用一句话写清判断、判定或证伪条件及目标期间，`reason` 说明事实与结论之间的关系。
7. `evidence` 为可回溯的材料名称、日期和链接或报告章节数组，待验证或证据不足可留空但须说明缺口。
8. 未完成事项沿原 ID 继续回应，不因复评而复制成新事项，也不为凑数量制造新问题。

以下仅示意新增字段，ID 和证据为占位值，不可直接导入：

```json
{
  "previous_snapshot_id": 101,
  "continuity": {
    "change_reasons": [
      {
        "field": "certainty_score",
        "type": "new_evidence",
        "reason": "新增回款证据支持现金转化改善，具体数值见对应财务章节。",
        "evidence": ["材料名称、发布日期、原文链接及页码"]
      }
    ],
    "previous_checks": [
      {
        "snapshot_id": 95,
        "check_id": "cash_conversion",
        "result": "pending",
        "reason": "原条件要求核对年度数据，相关年报尚未披露。",
        "evidence": []
      }
    ],
    "next_checks": []
  }
}
```

## 3. 业务规则

### 3.1 分数比较与事项承接分开处理

1. 分数默认比较同标的、同研究员、研究日期不晚于本次的最近快照，排序为 `report_time DESC, id DESC`。
2. 研究时固定 `previous_snapshot_id`，可说明原因后选择较早版本，导入时复核其存在性、归属和日期，禁止自引用或自动改绑。
3. 验证事项从同标的、同研究员、日期不晚于本次的全部有效结构化记录汇总，不只读取比较快照。
4. 按原事项引用归并历史，以 `(report_time, id)` 最新一条回应决定当前状态，无回应或最后状态为待验证、证据不足的事项均须承接。
5. 旧格式报告不新增也不结束验证事项，指定较早比较基准不能跳过其他已有未完成事项。
6. 生成和导入共用上述规则，期间新增历史导致待回应集合变化时提示补齐，不自动生成研究结论。
7. 无合法比较记录才允许空基准，有历史却漏填 ID、查询失败或结果截断均不能当作首次研究。
8. 历史补录须遵守当时可获得的信息范围，同日资料截止时间仍由研究过程核对。

### 3.2 事项状态与来源失效

1. 验证条件尚未到期用 `pending`，时点已到但证据不够用 `insufficient_evidence`，条件已有结论才用支持、削弱或证伪。
2. 已完成事项继续跟踪下一阶段时创建新期间或新条件，不改写原事项；需要重审旧结论时说明原因并保留原引用。
3. 原事项仍存在时核验其标的、研究员及日期，跨标的、跨研究员、未来记录和首次出现的无效引用一律拒绝。
4. 需回应事项的原始来源已删除但仍有此前成功入库的回应时，沿该已知引用以 `insufficient_evidence` 承接并注明来源缺失，不阻断后续评分。
5. 来源失效例外只适用于系统已有引用，不能凭本次报告自称“以前验证过”放行，也不能据缺失原文宣称支持或证伪。
6. 若原事项及所有历史引用均被删除，则无法恢复，不补造判断；报告正文缺失但结构化事项仍在时可继续验证。
7. 比较快照被删除时，已有报告展示来源缺失，新报告须重新确认可用基准，不由系统静默替换。
8. 旧报告只有正文观察点时在正文复盘，不补造历史 `check_id`，从本次开始建立结构化事项。

### 3.3 变动说明

1. 每个变化维度及等级都须有对应原因，分数不变也须回应旧事项并说明重大逻辑或风险变化。
2. 无新事实仍可纠正旧判断或旧计算，但须引用旧依据并说明修正理由，文字润色不算研究变化。
3. 六维不变而总分改变时必须说明计算纠错或方法变化，不得冒充经营改善。
4. 风险额外降级即使发生在首次研究或最终等级未变也须说明依据，本次反证检查不自动触发降级。
5. 分差读取时统一计算，不用当前公式重算历史；方法不同或未核实时仅展示记录值差异。

### 3.4 导入与兼容

1. 先按真实 `report_id` 查重，已入库报告直接返回保存结果，不因后来的历史变化重新校验或覆盖。
2. 新报告校验、快照追加及回流改为 `parsed` 必须在同一事务内完成，任一失败均回滚业务写入。
3. 并发仅对来源唯一键冲突执行回滚后读取已有结果，其他异常正常报错，不误报导入成功。
4. 六维和总分必须是完整、有限的 0–10 数值，拒绝布尔值、缺失和越界，资料不足的报告保存原文但不补 0 入库。
5. 研究员须与回流元信息一致，标题确定研究日期，JSON 同时提供日期时必须一致。
6. 校验数组、枚举、非空理由、唯一引用和变化覆盖，错误定位到具体字段或事项，不把无效连续性丢弃后继续导入。
7. 出现 `continuity` 或 `previous_snapshot_id` 任一键即执行新格式校验，两键须齐全且 `continuity` 不能为 `null`。
8. 两键均缺失的旧格式仍可导入合法评分并绑定真实来源，但不生成或覆盖连续性记录。
9. 现有报告顶层其他研究字段继续保留原文，连续性对象内误拼字段报错，普通评分写入入口复用同一领域规则。
10. 结构与引用校验不等于研究结论被证明，语义、证据充分性及方法适用性仍由研究过程负责。

兼容边界：改版前无来源 ID 的快照不能自动去重，不同报告 ID 不按同标题合并，缺字段也不能自动识别为“新版技能漏输出”。

### 3.5 精确读取与界面

1. 云端参考文件关于不支持 `score_history` 的说明需按实际服务修正，但当前按日合并的趋势序列仍不能作为完整研究历史。
2. 新增领域只读能力 `stock_analysis.get_score_context`，按标的、研究员、研究日期和可选比较 ID 返回基准、待回应事项及来源状态。
3. 待回应事项使用稳定排序分页，返回总数与续页信息，全部读取后才视为完整，历史变化时重新核对。
4. Web/H5 复用评分列表和详情入口并按需扩展精确 ID 查询，比较结果与 MCP 共用领域逻辑，不再单独建设页面上下文接口。
5. 趋势图保留每日代表点，明细支持同日版本，已有报告始终按保存的基准显示分差。
6. 在原评分明细中就地展示分差和原因，展开查看验证事项及原报告，异常使用简短状态，不增加标语或大块说明。
7. 保持现有功能、ECharts 和共享 H5/APK 路径，兼顾直观操作、实现复用、清晰标签、可识别状态及键盘访问。
8. 未关联来源、历史不完整、来源删除和口径未核实须如实显示，不冒称首次研究或验证通过。

### 4.1 上线和验证

1. 先完成迁移、导入和读取兼容，再启用云端新契约，保留原 ZIP 并区分后续版本。
2. 上传继续使用原文及独立回执，`received` 仅表示收到，不能代替评分导入成功。
3. 先运行纯逻辑与模拟数据检查，数据库并发和约束验证须在符合 AGENTS.md 备份及授权要求的环境执行。
4. PostgreSQL 使用 `tools/migrations/YYYY-MM-DD_stock_score_continuity.sql`，SQLite 增量补列建索引，不重建或清空表。
5. 任何数据库修改前按 AGENTS.md 备份本地数据库，线上另备份 PostgreSQL，清理或重置的具体命令仍须单独批准。
6. UI 验证覆盖浅色、深色、移动端、用户操作与 AI 可识别性，未验证项明确记录。

### 4.2 回退顺序

1. 暂停所有评分导入入口并处理完在途任务，上传可继续但新报告保持待处理。
2. 停用新版云端输出并核实实际生效状态，期间收到的新版报告保留原文、不转换成旧格式。
3. 再回退后端和界面，保留新增列及已存数据，回退版本须保留对新格式的明确拒绝检查。
4. 若回退版本无法区分新旧格式，则保持评分导入暂停，兼容能力恢复后再处理积压报告。
5. 暂停措施须在代码回退后仍有效，并覆盖单条、批量及其他评分写入入口，线上启停只使用项目根目录标准脚本。

## 5. 验收清单

| 场景 | 必须满足 |
|---|---|
| 有历史且评分变化 | 固定基准，每个变化维度和等级有原因及证据 |
| 分数持平、独立总分纠错或风险降级 | 分别保留验证进展、纠错说明或风险依据 |
| A 提出事项，B 为旧格式，C 复评 | C 仍能回应 A 的未完成事项 |
| A/B 均有事项，本次选择更早比较基准 | 分数按指定基准比较，未完成事项不随之减少 |
| 连续多期没有新问题 | 可以新增 0 条，旧事项仍按原 ID 承接 |
| 来源删除但已有合法回应 | 标记证据不足继续承接，新伪造引用仍拒绝 |
| 原事项及全部引用删除 | 明确无法恢复，不补造历史 |
| 重复引用、漏回应、无效结构或非法分数 | 定位报错，不静默降级或补零 |
| 历史在生成与导入之间变化 | 提示补齐新增事项，不自动改分或换基准 |
| 待回应事项超过单次读取上限 | 分页取得全部结果，截断不冒充完整 |
| 同报告重复或并发导入 | 返回同一快照，回流状态一致，无部分写入 |
| 旧格式、同日版本、多研究员、历史补录 | 保持兼容、归属清晰，比较和事项口径一致 |
| Web、H5、MCP 与云端联调 | 三期事项可承接，原有功能和上传行为不回退 |
| 回退时仍收到新版报告 | 原文保留待处理，旧导入器不会静默丢弃新字段 |
